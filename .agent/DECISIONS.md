## DEC-010：语音唤醒使用托盘后台进程，不注册开机自启动

- 日期：2026-09-24
- 状态：已确认并实施
- 背景：用户希望关闭可见界面后仍能喊“小鱼”唤出伙伴，但明确不需要 Windows 开机自启动，也不希望日常使用依赖桌面快捷方式。
- 决定：语音唤醒开启时，关闭主窗口仅隐藏到托盘，主进程和本地唤醒继续运行；托盘“退出一隅”才彻底退出。应用保持单实例，后台已有实例时再次启动只显示主窗口。不开机自启动，重启后需从安装目录或开始菜单手动启动一次。
- 备选方案：Windows 登录自启动；独立 Windows Service；程序完全退出后仍唤醒。
- 选择理由：没有运行中的进程就无法监听麦克风；托盘模式能满足关闭界面后的唤醒，又不会在用户未明确要求时随系统启动。独立服务仍属于后台常驻且会扩大安装、权限与升级复杂度。
- 影响：用户必须保留安装目录中的程序本体，但可以删除桌面快捷方式；彻底退出后不再承诺语音唤醒。开启语音唤醒会改变主窗口关闭语义，设置和帮助中心必须明确说明。
- 用户确认：用户明确选择“不需要开机自启动，关闭主界面后托盘继续唤醒”的方案。
- 关联：`apps/desktop/src-tauri/src/lib.rs`、`backgroundRuntime.ts`、`CompanionVoiceSettings.tsx`、`docs/product/06-动态伙伴与隐私安全层.md`

## DEC-009：M6 改为自动门禁优先，并以正文资料标记驱动 AI 脱敏

- 日期：2026-08-11
- 状态：已确认并实施
- 背景：用户反馈十项场景和连续七天试用过于繁琐，希望之后尽量少人工验收；同时希望从正文选词直接建立资料并用于 AI 作图脱敏。
- 决定：移除 M6 固定场景、连续天数、环境矩阵和跨设备演练门槛；保留自动质量门禁，安装后按真实工作方式自然体验。正文使用 Tiptap `entityReference` mark 关联人物、地点或事件，可直接建档；AI 调用前默认只替换已标记资料并显示实际发送预览。
- 备选方案：保留打卡但改为可选；用名称匹配自动识别全部敏感词；在 provider 服务端脱敏。
- 选择理由：降低用户验收负担；显式标记比名称猜测更可控，也能同时服务资料沉淀、反向引用和隐私预览，且不要求把原文交给额外服务处理。
- 影响：M7 不再被七天或跨设备人工项阻断；旧 `settings.acceptance` 不再新写入。脱敏保护边界是“已标记资料”，未标记敏感信息必须通过发送预览识别。
- 用户确认：用户在 `1.0.0` 体验反馈中明确提出以上两项变化。
- 关联：`docs/体验反馈与需求补充.md`、`EntityReferenceMark.ts`、`entityPrivacy.ts`、`docs/1.0.0-验收与发布说明.md`

## DEC-008：可移动资料库与本机秘密使用不同根目录

- 选择理由：兼顾用户可控位置、已有资料库接入和秘密隔离，并避免在缺少中断恢复协议时实施高风险目录搬迁。
- 影响：跨设备使用完整备份恢复，API Key 必须在新设备重新配置；已有库改位置是明确已知限制。
- 用户确认：属于用户已同意的 M6 首次向导、跨机器恢复与安全范围。

## DEC-044：自主能力采用持久任务计划与本地确定性执行器

## DEC-041：流式模型文本区分可撤销预览与最终可朗读回答

- 日期：2026-09-25
- 状态：已确认并实施
- 背景：DeepSeek 的同一次流式响应可能先输出普通文本，随后才返回 Tool Call；工具执行后又会生成基于真实结果的最终回答。把所有 delta 直接送入 TTS 会依次朗读工具前草稿和最终答案。
- 决定：每个模型步骤的流式文本在响应类型确定前视为可撤销界面预览；若该步成为 Tool Call，Runtime 发出 reset 并清除临时文字。TTS 只消费 Agent 最终返回的文本，再按句合成和顺序播放，不朗读工具前草稿。
- 选择理由：模型协议在流结束前不能可靠保证后续不会出现 Tool Call；任何基于标点、时间或首包内容的提前朗读都可能泄露错误草稿。最终文本提交屏障牺牲少量工具型回答的首音延迟，换取只读真实整合结果的确定性。
- 影响：普通文字仍逐段显示；Tool 型回答的临时预览可被清空，最终回答重新流式显示。语音从最终答案确认后开始，但仍分句合成、顺序播放并支持暂停、中止和打断。
- 用户确认：用户实机发现工具前后两部分被重复朗读，明确认为该行为不正确并要求修复。
- 关联：DEC-022、DEC-025、DEC-034

## DEC-045：透明 WebM 改用受控 Range 协议而非整文件 IPC Blob

- 日期：2026-09-30
- 状态：已确认并实施
- 背景：动作库扩充前，现有高分辨率 VP9 Alpha WebM 已会在首次读取时造成明显停顿。仅把“启动全部加载”改为“播放时按需加载”，仍需经 Rust 整文件读取、IPC 复制、ArrayBuffer 与 Blob 创建，因而把卡顿从启动转移到了首次播放；固定数量的热缓存也只会改变卡顿发生时机。
- 决定：视频由仅限 `companion` WebView 的 `yiyu-companion` 内部协议提供。协议只接受主窗口登记在 `CompanionAssetScope` 中的素材 ID，经仓储解析固定 videos 目录，不接收任意路径；在后台线程读取文件，支持标准单段 byte Range，并把单次响应限制为最多 1 MiB。WebView2 直接把协议 URL 交给 `<video>` 分段缓冲和解码，静态立绘继续沿用原受控 IPC Blob。视频响应提供匿名 CORS，使末帧 canvas 兜底仍可工作。
- 备选方案：启动时读取全部 WebM；只在首次播放时整文件读取；后台预热固定 8 个 Blob；直接暴露资料库绝对文件路径给 Tauri asset 协议。
- 选择理由：Range 协议消除大文件在 Rust→前端 IPC、ArrayBuffer 和 Blob 之间的整块复制，不需要让大量视频常驻渲染进程内存；素材 ID 白名单与固定仓储路径继续保持原安全边界，也不增加用户可见设置。
- 影响：WebM 播放依赖 WebView2 对内部协议的 Range 请求与 VP9 Alpha 解码；首帧等待、末帧 canvas、placement 和动作调度不变。真实设备仍需验证首次播放延迟、透明合成和长时间内存占用。
- 用户确认：用户指出即使尚未加入新增动作，现有素材也已卡顿，并确认采用受控本地视频流协议方案。
- 关联：DEC-034、DEC-040、R-019、R-024、R-028
