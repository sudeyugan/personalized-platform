云中枢正在逐步部署，已有本机HTTPS为401及用户反馈移动网络可访问的证据，尚未完成证书续期与实际多端验收。2026-10-21用户已购腾讯云轻量服务器，并通过OrcaTerm确认Ubuntu 24.04.5/x86_64、Node v24.22.0/SQLite检查通过、Certbot 5.8.0，UFW未启用；无域名，已取得公网IPv4可信证书。旧Tailscale测试连接与测试待发队列已按用户明确授权丢弃，本机资料和旧服务文件保留；独立开展云端测试，不迁移这份测试身份。手机不要求同一Wi-Fi、IPv6或Tailscale。

白名单部署包已由用户在服务器校验通过；按专用账户安装、私密初始化与回环启动步骤执行后，用户回贴无凭证POST最终HTTP=401、127.0.0.1:17839监听。内部鉴权与本机HTTPS均已通过，移动网络访问获用户确认；自启动/重启、续期/重载与真实同步仍待验证，校园网访问问题未解决；不重复初始化。没有直接SSH接入、索取服务器密码/首次连接凭证或把本机资料库打包上传。

## 通路与隐私

Windows / Android → 受信任 HTTPS → Caddy → `127.0.0.1:17839` Node24 中枢。不把17839暴露公网，不启用任意来源CORS、TLS忽略、隧道公开或远程命令执行。

中枢仅保存端到端加密的记录、必要设备/时序元数据与凭证摘要；配对设备持有解密密钥。普通聊天也属于同步记录，端侧可读；“仅本机”会话、浏览器私人查询、模型/语音Key、Cookie和原始录音不因同步获准而上传。云盘快照仍含元数据及凭证摘要，备份同样须私下保护。服务端不能补回遗失的端侧密钥。

模型调用独立于同步：DeepSeek接收本会话必要文字，ElevenLabs接收录音及朗读文本。中枢密文不代表模型零明文、服务商零保留。此批不实现跨设备应用代理或文件通道。

## 服务器部署步骤与剩余验证

1. 使用受支持的Linux LTS、Node24与Caddy官方来源。此服务器已由用户安装Node24到`/opt/yiyu-node-24`，入口为`/usr/local/bin/node`；仓库通用模板仍用`/usr/bin/node`，本次部署包已按实际路径调整。Caddy v2.11.7已由用户回贴active；不把安装依赖等同于中枢/公网部署完成。
2. 创建专用`yiyu-hub`无登录服务账户；代码放`/opt/yiyu-hub/src/`，只读归管理员；数据放`/var/lib/yiyu-hub/`，归服务账户、0700。此服务无npm运行依赖，不把整个含个人资料的工作区传上服务器。
3. 部署文件在`apps/sync-hub/deploy/`。先人工检查`yiyu-hub.service`和`Caddyfile`；将示例域名替换为本人控制、已解析到服务器的域名。不要把`hub.example.com`原样启用。Caddy证书存储须持久化，不加入源码。
4. 全新空中枢才在私密SSH终端以服务账户执行下方初始化。一次性管理凭证只显示在终端，不进聊天/截图/日志；保存到安全离线位置。**迁移已有中枢不执行初始化**。

```sh
sudo -u yiyu-hub /usr/bin/node /opt/yiyu-hub/src/main.mjs --init --data /var/lib/yiyu-hub
```

5. 授权实际部署后才安装服务并启动。模板用只读系统、私有临时目录、无新增特权和资源上限；启动前确认初始化数据完整。Caddy使用独立的既有官方服务，先`caddy validate --config 路径`，不覆盖这台服务器其他站点配置。
6. 公网仅开放HTTPS所需443及证书签发/跳转所需80；SSH限制管理员来源。**不开放17839、SQLite、管理面板或任意文件服务**。不在反向代理记录请求体、Authorization或聊天原文；Caddy模板丢弃访问日志，系统运行错误日志仍需限制读取与保留。
7. 启动后先用正常TLS无凭证POST检查401；再用临时测试空间验证配对/撤销/同步与重启。真实资料前检查证书、磁盘权限、服务账户、备份和关闭流程；不以`curl -k`或关闭证书验证“通过”。

无域名路径不能原样启用示例Caddyfile：需先准备只用于ACME的HTTP验证入口，取得公网IPv4证书，再配置Caddy加载证书、私钥的最小读取权限及Certbot续期后的部署/重载钩子，验证自动续期。IP证书寿命约6天，不把只申请到一次证书当作完成；不承诺跳过云厂商或适用备案要求。依据[Let's Encrypt IP证书与Certbot说明](https://letsencrypt.org/2026/03/11/shorter-certs-certbot)。

IP直连还需验证空SNI场景：客户端可能不发送ServerName，公网IP经云NAT或回环测试时与Caddy实际本机地址不同，不能仅以配置语法通过证明选证书正确。单IP入口可在全局设置`default_sni 本人证书中的公网IPv4`，保持证书IP匹配与可信链校验；这不是关闭TLS校验。依据[Caddy默认SNI选项](https://caddyserver.com/docs/caddyfile/options#default-sni)。首次现场为validate通过、回环curl35/internal error失败；提出补默认SNI后，用户已确认本机正常TLS无凭证POST为401，但校园网443尚未建立TCP，不能把本机通过称为公网修复。

HTTPS行为参考[Caddy官方反向代理文档](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)与[访问日志配置](https://caddyserver.com/docs/caddyfile/directives/log)。当前HTTP验证入口本机200、HTTPS本机401已有用户确认；校园网公网TLS与自动续期/重载仍待验证。

## IP证书自动续期与重载（待服务器执行验证）

当前Caddy只读`/etc/caddy/yiyu-tls/`中的root:caddy、0640副本，不放宽整个Let’s Encrypt目录。需要同时验证Certbot定时器、CA续期和部署钩子；只签发成功或只看到定时器不能视为完成。保留80上的ACME验证目录，不能因校园网无法访问80就关闭它。

在服务器以`sudo nano /etc/letsencrypt/renewal-hooks/deploy/50-yiyu-caddy`创建以下内容；若已有内容，先核对，不直接覆盖。本脚本不含实际IP、账户或秘密，仅接受指定证书路径：

```sh
#!/bin/sh
set -eu
umask 077

case "${RENEWED_LINEAGE:-}" in
    /etc/letsencrypt/live/yiyu-ip|/etc/letsencrypt/live/yiyu-ip/) ;;
    *) exit 0 ;;
esac

/usr/bin/install -o root -g caddy -m 0640 \
    /etc/letsencrypt/live/yiyu-ip/fullchain.pem \
    /etc/caddy/yiyu-tls/fullchain.pem
/usr/bin/install -o root -g caddy -m 0640 \
    /etc/letsencrypt/live/yiyu-ip/privkey.pem \
    /etc/caddy/yiyu-tls/privkey.pem

/usr/sbin/runuser -u caddy -- /usr/bin/caddy validate \
    --config /etc/caddy/Caddyfile
/usr/bin/caddy reload --config /etc/caddy/Caddyfile --force
printf '%s\n' 'YIYU_CERT_RELOADED'
```

文件归root:root、0750；先以`sh -n`检查语法，再用`sudo env RENEWED_LINEAGE=/etc/letsencrypt/live/yiyu-ip /etc/letsencrypt/renewal-hooks/deploy/50-yiyu-caddy`试跑现有证书，成功才继续。显式`--force`保证配置文本不变时也重新加载证书，不重启或中断中枢。若验证/复制失败则停止并查看错误，不扩大权限或忽略退出码。

Snap安装需核对`sudo systemctl enable --now snap.certbot.renew.timer`、`systemctl list-timers --all snap.certbot.renew.timer`；若该单元不存在或不能启动，先核对Snap安装，不随意添加重复cron。用`sudo /snap/bin/certbot renew --cert-name yiyu-ip --dry-run --run-deploy-hooks`演练；该参数在验证成功后用当前正式证书运行钩子，不把测试证书部署给Caddy。检查续期成功、钩子输出及其退出情况，再用正常TLS无凭证POST确认仍为401，才记录这一维护链通过。依据[Certbot续期与钩子](https://eff-certbot.readthedocs.io/en/stable/using.html#renewing-certificates)和[Caddy强制重载](https://caddyserver.com/docs/command-line#caddy-reload)。目前这些步骤仅准备好，未有服务器执行证据。

## 备份与恢复

维护工具使用SQLite在线备份，覆盖WAL中的已提交操作，不直接复制正在写入的主库。目标文件必须不存在，恢复目录必须是新目录；不会覆盖运行库或旧备份。备份/恢复失败可能留下候选文件，应核对后人工处理，不自动删除。

```sh
node apps/sync-hub/src/maintenance.mjs backup --data 原中枢目录 --to 新备份文件的绝对路径
node apps/sync-hub/src/maintenance.mjs inspect --file 备份文件的绝对路径
node apps/sync-hub/src/maintenance.mjs restore --file 备份文件的绝对路径 --to 新数据目录的绝对路径
```

维护命令只打印有效设备数和密文操作数，不输出密钥/凭证/内容。恢复输出0700目录、0600数据库；在目标服务器用服务账户执行，或由管理员核对归属。恢复不重新生成空间/设备/令牌。Node实现依据[官方SQLite备份API](https://nodejs.org/api/sqlite.html)。

## 可选：保留有效中枢身份迁到云端

以下只适用于仍需保留的有效同步空间；当前用户已明确放弃的Tailscale测试连接不走此迁移流程，也不迁移其队列或密钥。

1. 先在客户端保存管理恢复包到安全离线位置。不要发给Agent、公共网盘或源码。更新全部配对客户端后再使用新增普通聊天集合；旧预览客户端会对未知集合拒绝应用，不静默丢字段。
2. 在明确维护窗口停止旧中枢写入，取得最终备份；用新目录恢复到云端。**两个分叉中枢不能同时接受写入**。可先做在线预演，但最终切换必须冻结旧端再备份，不能用过期快照。
3. 新端保留同一空间、设备与密文历史，配置可信HTTPS。旧端保持停止，勿删原数据，作为回滚副本。
4. Windows在“高级连接选项 → 迁移或更换云端地址”、手机在“中枢迁址”填写新HTTPS地址。首次确认会向所填地址发送本设备凭证进行只读核验；确认归本人所有。核验前`envelopes`为空，不发送待上传记录。
5. 客户端校验空间、连续游标，并用原密钥解密核验已收到游标位置的操作。地址无效、空库、过期历史、错误密钥或本机保存失败，原连接不改变；成功只改地址，保留密钥/设备/队列/分支选择，随后正常补传。它不是逐字节整库哈希认证，也不能合并两台已分叉运行的中枢。
6. 电脑与手机移动网络分别往返一条测试记录、断网修改再补传、撤销临时设备、服务器重启和恢复演练，才算真实跨网通过。目前没有实际服务器/手机证据，不标M13.2完成。

回滚前先停止新端，保存其最新完整备份；不能直接启动旧快照造成历史分叉或游标回退。没有自动清队列、降游标、断开重配或删除数据的“修复”。
