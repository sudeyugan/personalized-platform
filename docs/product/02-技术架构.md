# 一隅：技术架构

版本：0.1  
面向读者：开发者与 AI 编程工具

## 1. 架构目标

- Windows 10/11 原生桌面应用，UI 采用网页技术。
- 本地优先、离线可写，云端能力以适配器形式存在。
- 写作数据与具体编辑器、AI 服务商和云服务商解耦。
- 模块默认最小权限，不让未来插件直接获得整个文件系统或所有文稿。
- 项目结构适合分阶段由 AI 编程工具实现和测试。

## 2. 推荐技术栈

| 层 | 选择 | 理由 |
|---|---|---|
| 桌面容器 | Tauri 2 + Rust | Windows 桌面能力、安装包、较小体积、前后端权限边界 |
| 前端 | React + TypeScript + Vite | 生态成熟、组件化清晰、AI 工具支持好 |
| 状态 | Zustand（界面状态）+ TanStack Query（异步数据） | 避免把持久化业务逻辑塞进全局 UI 状态 |
| 路由 | React Router | 模块路由与深链接 |
| 编辑器 | Tiptap（基于 ProseMirror） | 富文本与块节点可结合，自定义扩展、JSON 文档结构 |
| 本地数据库 | SQLite | 单用户本地数据、事务、迁移、全文索引和备份能力 |
| 后端访问 | Rust Repository/Service 层 | 加密、文件、备份、导入导出和权限集中在可信端 |
| 搜索 | SQLite FTS5（仅非加密、已解锁可索引内容） | 本地全文搜索；加密内容锁定时必须移出索引 |
| 样式 | CSS Variables + CSS Modules（或 Tailwind，仅选其一） | 主题令牌与模块隔离；避免同时维护两套体系 |
| 测试 | Vitest + Testing Library + Playwright + Rust tests | 单元、组件、端到端和后端逻辑分层验证 |
| 包管理 | pnpm | workspace 与依赖锁定，适合未来插件 SDK |

### 2.1 为什么推荐 Tauri，而不是直接做网页或 Electron

纯网页无法自然满足本地资料库、可靠文件备份、系统窗口和未来桌面伙伴。Tauri 在 Windows 使用 WebView2 渲染网页界面，能够生成 MSI 或 NSIS 安装包，并通过 capability/permission 限制前端能调用的桌面能力。官方资料见 [Tauri Windows 安装包](https://v2.tauri.app/distribute/windows-installer/)、[Tauri capabilities](https://v2.tauri.app/security/capabilities/) 与 [开发环境要求](https://v2.tauri.app/start/prerequisites/)。

建议第一阶段构建 NSIS 的按用户安装包，不要求管理员权限。便携版不作为首要交付物，但架构不硬编码安装路径，后续可增加。

### 2.2 为什么推荐 Tiptap

Tiptap 提供 React 集成、JSON 内容树和扩展机制，能实现“普通输入像 Word，图片/引用等特殊内容为可移动块”的混合体验。正文以规范化 JSON 保存，导出时再转换为其他格式。参考 [Tiptap React 文档](https://tiptap.dev/docs/editor/getting-started/install/react)、[核心概念](https://tiptap.dev/docs/editor/core-concepts/introduction/) 和 [扩展机制](https://tiptap.dev/docs/editor/core-concepts/extensions)。

注意：第三方的高级 DOCX 导入/导出扩展可能涉及商业许可。第一阶段应把导入导出放在独立适配层，先验证开源实现和许可证，不让编辑器绑定某个付费服务。

## 5. 模块系统

### 5.1 第一阶段：可信内置模块

模块通过清单注册，但代码与主应用一起构建：

```ts
interface ModuleManifest {
  id: string;
  nameKey: string;
  version: string;
  routes: ModuleRoute[];
  navigation?: NavigationContribution[];
  homeCards?: HomeCardContribution[];
  settingsPages?: SettingsContribution[];
  requestedCapabilities: CapabilityId[];
  dataSchemaVersion: number;
}
```

应用 Shell 只认识清单贡献，不在代码中写死所有模块入口。模块停用后：

- 隐藏路由贡献、导航和首页卡片。
- 停止非必要后台任务。
- 保留模块数据。
- 禁止模块继续访问未授权资源。

### 5.2 第二阶段：模块创建器

可视化模块创建器生成声明式 schema，而不是任意 JavaScript：

- 页面与视图（表格、卡片、详情、日历）。
- 字段类型和关系。
- 按钮触发的受限动作。
- 自动化条件与动作。

声明式设计便于迁移、权限检查和备份。

### 5.3 第三阶段：开发者插件

- 插件包必须有 manifest、版本、签名/来源、数据迁移和权限声明。
- 插件运行在隔离 WebView/Worker 或外部受控进程，不与主 UI 共用无限权限上下文。
- 文件、网络、AI、文稿和系统操作均通过 host API。
- 安装和升级展示权限差异；升级新增权限需要再次授权。
- 第一阶段严禁为了“预留插件”而引入任意代码加载。

## 6. 编辑器架构

### 6.1 内容格式

- 数据库内的当前正文保存为版本化的 Tiptap/ProseMirror JSON。
- 每份文档记录 `schema_version`。
- 只允许由已注册 schema 定义的节点进入正式存储。
- 保存前规范化 JSON，未知节点不得静默丢弃；迁移失败时以只读方式打开并允许原始导出。

建议第一阶段节点：`doc`、`paragraph`、`heading`、`text`、`bulletList`、`orderedList`、`listItem`、`blockquote`、`horizontalRule`、`hardBreak`、`link`、`imageAsset`。

### 6.2 保存管线

```text
用户编辑
  → 前端内存状态
  → 300–800ms 防抖
  → saveDocument(expectedRevision, JSON)
  → Rust 校验 schema/权限/磁盘状态
  → SQLite 事务更新 current_document + revision counter
  → 必要时写入历史版本
  → 返回 committedRevision
```

- 使用乐观并发字段 `expectedRevision`，避免两个标签页静默覆盖。
- 保存状态必须以 Rust 返回的已提交版本为准，不以编辑器 `onUpdate` 为准。
- 关闭窗口前 flush；异常退出使用恢复日志/草稿文件作为第二道防线。

### 6.3 历史版本

- 当前内容与历史版本分表。
- 自动版本根据时间和显著变更创建，避免每次按键生成完整快照。
- 初版可保存压缩后的完整 JSON；数据量验证后再考虑增量差异。
- 恢复动作创建新版本，不修改历史行。

## 7. 数据与事务

- SQLite 开启 foreign keys。
- WAL 模式需要结合备份与关闭流程测试；不可只复制主 `.db` 文件当作备份。
- 使用 SQLite Online Backup API 或事务一致的导出方式创建数据库快照，参考 [SQLite Online Backup API](https://www.sqlite.org/backup.html)。
- 每次 schema 迁移记录 `migration_id`、开始/完成状态和前置快照。
- 数据库层只存素材的逻辑 ID 与相对路径，不存绝对路径。

## 8. 加密与秘密管理

### 8.1 威胁边界

目标是防止他人在未获密码时通过应用界面、资料库文件、搜索索引或普通备份看到指定作品内容。第一阶段不宣称抵御已控制当前 Windows 会话、键盘记录器或内存取证的高级攻击。

### 8.2 作品级加密建议

- 普通数据库只保留随机 `vault_id`、加密状态和最少的匿名系统字段。
- 真实标题、正文、资料关系、封面、版本和相关附件放进该作品的加密 vault。
- 密码经 Argon2id 派生主密钥；内容使用经过审查的 authenticated encryption 实现（建议 XChaCha20-Poly1305），每个文件/记录使用独立随机 nonce。
- 不自行实现密码学算法；使用成熟 Rust 密码库并锁定版本。
- 解锁密钥只在内存中存在，休眠、锁屏、超时或退出时清除。
- 明文不得写入日志、临时目录、崩溃报告、剪贴板历史或缩略图缓存。
- 锁定前删除该作品的 FTS 条目；加密作品搜索只在解锁后于受控范围执行。

SQLCipher 可作为“整个资料库加密”的未来备选，它为 SQLite 数据库提供整库加密；但当前需求是作品级独立隐藏，因此不要未经原型验证就把作品级模型绑死在整库方案上。参考 [SQLCipher 项目说明](https://github.com/sqlcipher/sqlcipher)。

### 8.3 API Key

- 使用 Tauri Stronghold 或 Windows Credential Manager 保存 AI 密钥，不进入 SQLite 普通表、日志或备份。Tauri 提供 Stronghold 密钥存储插件，见 [官方文档](https://v2.tauri.app/plugin/stronghold/)。
- 设置页面只显示掩码和最后验证时间。
- 日志自动清理 Authorization header、请求正文和密钥字段。

## 9. AI 适配层

```ts
interface TextModelProvider {
  id: string;
  listModels(): Promise<ModelInfo[]>;
  complete(request: TextGenerationRequest): Promise<TextGenerationResult>;
  testConnection(): Promise<HealthResult>;
}

interface ImageModelProvider {
  id: string;
  listModels(): Promise<ModelInfo[]>;
  generate(request: ImageGenerationRequest): Promise<ImageGenerationResult>;
  testConnection(): Promise<HealthResult>;
}
```

`ChapterImpressionService` 负责业务流程，provider 只负责服务商协议：

1. 读取明确选定的章节版本。
2. 构造待发送预览和权限确认。
3. 生成/编辑提示词。
4. 调用图片 provider。
5. 将候选图写入临时隔离区。
6. 用户确认后导入素材库并记录 provenance。

所有 AI 请求记录元数据，但默认不保存完整正文请求副本；加密作品尤其如此。未来本地模型只需实现相同 provider 接口。

## 10. 导入导出架构

```text
源文件 → Import Adapter → Canonical Document AST → 校验/预览 → 应用事务
应用数据 → Canonical Export Model → Export Adapter → DOCX/PDF/Markdown/Backup
```

- 规范 AST 与编辑器 JSON 分开，避免 DOCX 解析器直接操作 UI。
- DOCX 导入可评估 Mammoth 等库；DOCX 导出可评估 `docx`，PDF 可先生成 HTML 后由受控打印引擎输出。选型前必须用中文、图片、标题和分页 fixture 做 round-trip 测试并审查许可证。
- PDF 是阅读交付格式，不是恢复格式。
- Markdown＋图片与完整备份包才是长期可迁移格式。
- 导入先生成预览模型，用户确认后在单事务中落库。

## 11. 备份与恢复

- 备份由后台任务调度，但数据库快照、附件清单和校验必须在 Rust 端完成。
- 备份包临时写入同一目标磁盘的 `.partial` 文件，校验成功后原子重命名。
- 包内 manifest 记录应用版本、schema 版本、创建时间、条目数、哈希和加密说明。
- 恢复先解包到隔离目录、验证路径穿越和校验值，再进入预览。
- 合并恢复为每个实体生成冲突方案：跳过、复制为新 ID、以导入版本为新修订；默认不得覆盖。
- 自动备份保留策略先按数量和空间双限制，清理只删除明确识别为一隅备份的文件。

## 12. 云端存储接口

第一阶段只定义，不实现：

```ts
interface CloudStorageProvider {
  id: string;
  authenticate(): Promise<void>;
  putObject(key: string, bytes: Uint8Array, version?: string): Promise<RemoteObject>;
  getObject(key: string, version?: string): Promise<Uint8Array>;
  list(prefix: string, cursor?: string): Promise<Page<RemoteObject>>;
  deleteObject(key: string, expectedVersion?: string): Promise<void>;
  getCapabilities(): CloudCapabilities;
}
```

同步不能简化为复制正在使用的数据库。推荐同步不可变更的加密备份对象或设计正式同步日志；在冲突、端到端加密和断点续传验证完成前，仅提供“上传备份”的实验功能。

## 13. 音乐架构（下一阶段）

- `Track` 只引用逻辑媒体 ID，不假设来源。
- `PlaybackContext` 层级为 global → work → chapter → focus；更具体规则仅在用户允许自动切换时覆盖。
- provider 分为本地文件与在线目录；在线接口不得伪装成本地永久可用。
- 播放服务独立于 React 页面，切换模块不停止播放。

## 14. 虚拟伙伴架构（下一阶段）

拆成四层，避免角色 UI 与 AI 服务耦合：

1. `CharacterProfile`：身份、外观组合、资产与表现规则。
2. `CharacterRenderer`：静态立绘/动画/未来 Live2D 的渲染适配器。
3. `CompanionAgent`：对话、主动行为和工具调用。
4. `MemoryStore`：有来源、授权范围、置信度、过期和删除状态的记忆。

侧栏和桌面悬浮窗口共享同一个伙伴状态服务，但拥有不同 capability；桌面窗口不得自动继承主窗口所有文稿访问权限。

## 15. 安全基线

- Tauri capability 按窗口和模块拆分，采用 allowlist，不开放任意 shell。
- CSP 禁止未列出的远程脚本和 frame；远程 AI 响应只作为数据处理。
- 图片解码、ZIP 解包、DOCX 导入限制大小、条目数和路径。
- 所有 SQL 参数化；文件名与用户标题分离，磁盘路径使用随机 ID。
- 依赖锁定，CI 做漏洞与许可证检查。
- 日志默认不含正文、真实标题、图片提示词和 AI 请求体。
- 插件系统上线前单独进行威胁建模与渗透测试。

## 16. 测试策略

### 16.1 单元测试

- 中文字数、时间精度、关系、权限判定、版本保留策略。
- 编辑器 JSON schema 与迁移。
- 加密 round-trip、错误密码、篡改检测和密钥清理。
- 备份清单、哈希、路径安全和冲突规则。

### 16.2 集成测试

- SQLite 事务、迁移、FTS 隔离和 Online Backup。
- DOCX/Markdown/TXT 导入与三类导出。
- 图片复制、缩略图和孤儿清理。
- AI provider 使用本地 mock，不在 CI 调用付费服务。

### 16.3 端到端测试

- 核心写作、保存、恢复、备份和加密关键路径；优先自动化，不设置固定人工场景打卡。
- Windows 中文输入法、休眠/锁屏、断网、磁盘满和异常退出。
- 至少准备小型、10 万字单章和大资料库三种性能 fixture。

## 17. 版本与发布

- 应用版本使用 SemVer；数据 schema 单独递增。
- 每次发布生成 Windows NSIS 安装包、校验值、变更日志和迁移测试报告。
- 初期手动更新；自动更新需签名和回滚机制成熟后再启用。
- 正式对外分发前配置 Windows 代码签名，否则可能出现 SmartScreen 警告；Tauri 的相关说明见 [Windows 代码签名](https://v2.tauri.app/distribute/sign/windows/)。

## 18. 必须先做的技术验证（Spikes）

1. Tiptap 中文输入法、10 万字单章和图片节点性能。
2. DOCX 标题/图片导入与 DOCX/PDF/Markdown 导出质量及许可证。
3. 作品级加密 vault：锁定后数据库、索引、缓存和日志零明文。
4. SQLite 一致性备份、异常中断和完整恢复。
5. Tauri 双窗口/透明悬浮窗口原型，为未来桌面伙伴验证可行性，但不在第一阶段实现产品功能。

## 19. 0.1.0 实现注记（2026-08-08）

本节记录当前实现，不替代目标架构：

- 已实现 Tauri 2 + React/TypeScript/Vite、Zustand、Tiptap、Rust command → service → repository、SQLite migration/事务/revision、FTS5 和 NSIS。
- 未引入 TanStack Query、React Router、Playwright 和拆分 packages；当前规模下由 Shell 视图切换和 repository adapter 承担对应职责。
- SQLite 当前权威数据是 `library_state` 的版本化工作区 JSON；FTS5 `chapter_search` 和 `recovery/drafts` 独立维护。关系表与文档表仍是后续目标。
- M0 已验证 Argon2id + XChaCha20-Poly1305、SQLite 快照与转换 fixtures，但正式 Encryption/Backup/ImportExport Service 未在 `0.1.0` 暴露。
- 伙伴窗口结论为“调整”：在 capability 隔离完成前不创建产品窗口；当前仓库没有可运行的第二窗口入口。
- 前端已有 `zh-CN` 类型化词典入口，但页面仍存在内联中文；M3 UI 扩展前必须提取。

## 20. 0.2.0 实现注记（2026-08-09）

- M3 资料动作从主 Zustand store 中拆为 records slice；写作资料侧栏与关系面板为独立组件。

## 19. 伙伴 Agent 第一阶段架构（2026-09-18）

伙伴对话不再由 UI 直接调用一次性 `reply`，而是：

```text
CompanionPanel
  → Agent Runtime
  → ModelProvider
  → Tool Registry
  → Permission Engine
  → Application Service（受控读取/写入）
  → 当前 LibraryData 领域对象
```

- `ModelProvider` 只接收消息、裁剪后的 Context 和 Tool definitions，返回文本或结构化 Tool Call；它拿不到 Store、Repository、SQLite、文件或 Tauri command。
- Tool 元数据统一声明 name、description、JSON schema、capability、risk 和资料 scope。读取包括当前作品、章节、人物、地点与时间线；创建/修改覆盖待办、日历事务、日记、作品、章节、人物/地点/时间线资料、课表与伙伴记忆，每项都由 Registry 显式注册。
- Permission Engine 在 handler 前统一检查 capability/risk、作品/章节/资料授权和加密作品本次会话许可；读取 Application Service 只暴露已授权数据，写入 Application Service 仅暴露显式注册的可逆业务动作。Create/Modify Tool 还必须通过主界面或桌面聊天的逐次确认，确认不能替代资源 scope；删除、高风险、外部和系统能力统一拒绝。
- Runtime 默认最多执行 4 次 Tool Call；ToolNotFound、InvalidArguments、PermissionDenied、ExecutionFailed、AgentStepLimit 与 ModelError 使用统一结果/错误结构。每次执行写入 append-only session event，并持久化不含实际查询文本或结果内容的审计摘要。
- 内部 Runtime 直接调用 Registry，不通过 MCP。未来 MCP 只作为 Registry 的外部 adapter；Computer Use 仍必须新增高风险 capability 和确认流程，不允许复用任意 Rust command 或 shell。
- 当前 Agent 位于前端伙伴应用层，因为权威业务对象已由 Zustand 中的 `LibraryData` 管理，Rust `LibraryService` 只负责校验和持久化整份快照。若未来把业务查询下沉 Rust，应先新增明确的 Application Service，再由 Tool adapter 调用，不能让模型直接获得 Repository。

桌面形象同时改为 Renderer 类型联合：当前正式实现为 `portrait`，只读取一张主窗口注册的透明 PNG/WebP；`live2d` 仅保留类型扩展点，不加载 Cubism SDK。历史 `characterPackage` 字段继续兼容读取，但不再进入设置入口、桌面快照或活动渲染链路。

### M10 隐私与安全信任边界补充

- 应用以统一信任边界串联两类策略，但不把它们压缩成一个布尔值：隐私策略决定请求能否离开本机、自动上下文与最近对话是否携带、聊天历史是否落库；安全策略决定模型可调用的 capability、risk、资源 scope、逐次确认与审计。
- 所有 DeepSeek、朝问和在线语音请求在 Provider 调用前执行外部处理总出口检查；关闭后本地 Mock 仍可使用。关闭自动上下文或最近对话只裁剪模型请求，不扩大 Tool 权限；显式 Tool 查询仍需原有授权范围。
- API Key 继续由 Rust/Windows DPAPI 保存，不进入资料库、Prompt 或备份；伙伴子窗口继续使用最小 Tauri capability，不能访问资料库和长期密钥。审计只记录 Tool 名称、参数形状、权限结论、结果状态和耗时，不保存正文或 Tool 结果内容。
- 本地历史保留关闭时，当前窗口可显示本次会话的临时消息，但不会写入资料库或备份；重开窗口后临时消息消失。
- CalendarScheduleView 负责月历事务、日期摘要和周课表；DiaryView 独立归入创作空间；TodoView 负责一次性与重复任务。日期、课表周次和重复规则集中在 plannerDates，避免页面各自推导。
- 月历格只展示 calendarEvents 与日记索引；课程和待办按所选日期在右侧摘要。term 以本地日期计算第 1–16 周，课程周次支持全周、数字区间、单周和双周。
- 重复待办使用 completedDates 保存实际完成日，repeatDays 保存每周选择；完成次数、应完成次数和百分比从创建日至当前日期实时计算，不持久化可失真的汇总值。
- normalizeLibrary 为旧存档补 calendarEvents、term、repeatDays，并把旧 weekdays 规则转换为周一至周五；旧日记、课程、待办与完成记录不删除。
